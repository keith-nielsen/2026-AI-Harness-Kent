1. Metrics vs logs

There are four tools but only two kinds of data.

  • Metrics are numbers over time: request counts, latency, CPU, disk. They're cheap to keep and answer how much, how often, and is it getting worse.
  • Logs are individual events as text: one line per gateway call, per error, per service message. They answer what exactly happened, and why.

Rule of thumb: start in Grafana. Use metrics (Prometheus) to spot that something is wrong and logs (Loki) to find out why. Only touch Alloy to change what gets collected.

2. The four tools

Alloy

The log collector

Reads the systemd journal, turns fields into labels (unit, level, and for the gateway kent_event and identity), drops noise, and ships the rest to Loki.

Touch it when adding a log source or a label, or filtering noise. Live debugging shows lines passing through each stage.

Kent The right place for redaction (audit F-08) before data is stored.

Loki

The log store

Holds every service's logs, including one JSON line per gateway call: who called, which tier the router chose, success or failure, latency, tokens and error.

Ask it "why did that call fall back?", "what did Kent do at 02:00?", "was the gent identity refused?"

Kent The per-call audit trail. 30-day retention; F-04 covers making it tamper-proof and kept off the host.

Prometheus

The metric store

Every 15 s it collects counters and gauges from LiteLLM, the host (node_exporter), Loki, Grafana, Gitea, Alloy and itself.

Ask it "fallback rate this week?", "p95 latency?", "when will the disk be full?", "is every service up?"

Kent The source for alerts (F-05) and, later, spend per identity.

Grafana

The window and the alarm bell

Dashboards for everyday questions, Explore and Drilldown for investigations, and alerting (not set up yet). It stores no data of its own; it queries Loki and Prometheus.

Start here for almost everything.

4. Using Grafana

Explore, with Loki (Kent) selected

  1. Pick Loki (Kent) from the data source dropdown and switch the editor from Builder to Code.
  2. Paste a query from section 5 and press Run query (Shift+Enter). Set the time range wide enough (e.g. Last 3 hours).
  3. For logs next to metrics: click Split, set the new pane to Prometheus (Kent), and paste a query from section 6. Both panes share the time range.

Filtering by log level

Above log results is a log volume chart whose legend lists levels (info, warning, error, critical, debug). Click a level to show only it, Ctrl-click (Cmd on a Mac) to add or remove more, and click again to reset. In Logs Drilldown, the Labels tab → level has Include and Exclude buttons per level.

Levels come from journald's priority field. journald's notice level (between info and warning) isn't a Grafana level, so it may show as its own colour or as unknown. Alloy's live debugging has no level buttons; type e.g. level="error" into its search box instead.

Worth trying

  • Logs Drilldown → kent-litellm.service → Fields tab: routed_tier, status and identity, each with a breakdown chart.
  • Administration → Advisor: health checks for data sources and plugins (new in Grafana 13).

5. Loki queries (LogQL)

A query always starts with a label selector {…}. After that, | json parses each line into fields, unwrap turns a field into a number, and line_format rewrites the text. All of these were tested against this host.

Router decisions and outcomes (success, or failure and fallback)
sum by (routed_tier, status) (count_over_time({unit="kent-litellm.service", kent_event="llm_call"} | json | model_group="auto" [3h]))
p95 latency per tier; unwrap turns a log field into a number
quantile_over_time(0.95, {unit="kent-litellm.service", kent_event="llm_call"} | json | __error__="" | unwrap latency_s [3h]) by (model_group)
Prompt tokens per identity (the cost driver once Opus is billed)
sum by (identity) (sum_over_time({unit="kent-litellm.service", kent_event="llm_call"} | json | __error__="" | unwrap prompt_tokens [3h]))
Failed calls, with the reason (recorded since 28 Sep)
{unit="kent-litellm.service", kent_event="llm_call"} | json | status="failure"
Readable one-line view of every call
{unit="kent-litellm.service", kent_event="llm_call"} | json | line_format "{{.identity}} {{.model_group}}→{{.routed_tier}} {{.status}} {{.latency_s}}s"
The five noisiest services in the last hour
topk(5, sum by (unit) (count_over_time({job="systemd-journal"}[1h])))
Log lines per level in the last hour
sum by (level) (count_over_time({job="systemd-journal"}[1h]))

6. Prometheus queries (PromQL)

Paste these at 127.0.0.1:9090/query and click Explain to see each step of the query, or use them in Grafana. increase() handles the counter resets that happen whenever the gateway restarts.

Failures by exception class
sum by (exception_class) (increase(litellm_deployment_failure_responses_total[1h]))
Fallbacks to another tier
sum by (fallback_model) (increase(litellm_deployment_successful_fallbacks_total[1h]))
Where calls went (:8080 local model, :4010 oracle, api.anthropic.com Claude)
sum by (api_base) (increase(litellm_deployment_total_requests_total[1h]))
Gateway p95 latency from the histogram
histogram_quantile(0.95, sum by (le, model_group) (rate(litellm_request_total_latency_metric_bucket[1h])))
Free disk space forecast 7 days ahead (GB)
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 7*86400) / 1e9
CPU busy %
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])))

7. Terminal commands

Short lines, safe to paste one at a time. A line ending in | continues on the next.

Every gateway call from the journal (bypasses Loki)
F='fromjson?|select(.kent_event)|[.ts,.model_group,.routed_tier,.status]|@tsv'
journalctl -u kent-litellm --since -1h -o cat | jq -Rr "$F"
Scrape targets and their health
T=localhost:9090/api/v1/targets
curl -s $T | jq -c '.data.activeTargets[]|[.labels.job,.health]'
Latest gateway call records from Loki
L=localhost:3100/loki/api/v1/query_range
Q='{unit="kent-litellm.service",kent_event="llm_call"}'
curl -sG $L --data-urlencode "query=$Q" --data-urlencode limit=5 |
  jq -r '.data.result[].values[][1]'
Raw gateway metrics (anonymous requests get 401)
K=$(cat ~/.config/kent/litellm_operator_key)
curl -s -H "Authorization: Bearer $K" localhost:4000/metrics/ |
  grep '^litellm_deployment_total_requests_total'
What the monitoring services themselves are doing (Ctrl+C to stop)
journalctl -f -u kent-loki -u kent-prometheus -u alloy -u grafana-server

8. A worked investigation (28 Sep 2026)

During a tier test, every question seemed to be answered by the local model. This is how the tools found the cause.

  1. Loki: the router had escalated (14 smart, 4 frontier), but each escalation failed within about 2 ms and the gateway fell back to fast.
  2. Prometheus: litellm_deployment_failure_responses_total showed exception_class="UnsupportedParamsError", 16 times.
  3. Cause: Hermes sends reasoning_effort. The local tiers dropped it (drop_params: true) but the oracle tiers didn't, so LiteLLM rejected the call before sending it anywhere.
  4. Fix: drop_params on the oracle tiers, a test that fails if it goes missing, and the gateway now logs error_class and error on every failure, so the next silent fallback explains itself.

10. Not built yet

  • Alerting (audit F-05). First rule: "gateway fell back to fast more than N times in 10 minutes", which would have caught the bug above immediately. Grafana alerting needs no extra service.
  • Per-account access to telemetry. Loki (:3100) and the Alloy UI (:12345) answer any local account, including Kent's in the lab profile. Live debugging is opt-in (install/services/alloy/install.sh --live-debugging) and any re-run without the flag turns it off.
  • Page fetching for web research. SearXNG only searches; web_extract needs a backend (a self-hosted Firecrawl or a small local fetcher), sent through controlled egress.
  • Off-host, tamper-proof logs (audit F-04) and per-identity budgets (F-11).
